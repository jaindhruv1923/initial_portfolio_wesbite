Template Debugging & Remediation

Six Real Bugs Isolated & Resolved

Rather than styling over flaws, this project started with a systematic audit of the source template, catching critical DOM defects and architectural omissions that prevented the site from functioning as an actual business tool:

  • 01

    Dead CTA Anchors: "Find A Table" and "Book A Table" hero buttons both pointed to empty href="#" anchors. The reservation section itself lacked an HTML id. Assigned id="reservation" and wired smooth-scrolling event triggers across header, hero, and banner CTAs.

  • 02

    Form Field Name Collision (Data Loss): The guest-count select dropdown and the time-slot select dropdown both shared the identical attribute name="person". When submitted, the time value silently overwrote the guest count in standard URL-encoded form serialization. Disambiguated into name="person" and name="time".

  • 03

    Non-Existent Backend & Silent Failures: The original form attempted to submit to the current URL with no server endpoint to process it. Built an asynchronous Node.js + Express REST API backed by MongoDB Atlas, handling payload validation and persistent storage.

  • 04

    Jarring Page Refreshes: Standard HTML form submission forced a full-page reload, erasing user context and providing zero feedback. Intercepted the submit event with vanilla JavaScript fetch(), displaying an animated green toast confirmation on success and field-level validation errors on failure.

  • 05

    Missing Staff & Culinary Profile: The restaurant template lacked any section to introduce executive chefs and culinary credentials. Designed, engineered, and integrated a responsive 4-card "Our Chefs" showcase with CSS hover-reveal overlays.

  • 06

    Unconstrained Schema & Booking Collisions: The original inputs permitted negative guest counts and past dates. Implemented strict Mongoose schema validators (date ≥ today, party size between 1 and 20, regex phone/email verification).

Backend Engineering & Data Model

REST API Architecture & MongoDB Persistence

The backend was engineered as a decoupled, production-ready Express.js microservice adhering to RESTful resource conventions and strict schema sanitization:

HTTP Method Route Endpoint Description & Purpose Payload / Query Response Status
POST /api/reservations Creates new verified booking document in MongoDB Atlas with date slot lock. { name, email, phone, person, date, time, message } 201 Created
GET /api/reservations Retrieves chronological list of all active table reservations for restaurant management. Query: ?date=YYYY-MM-DD (optional filter) 200 OK
GET /api/reservations/:id Fetches specific booking by MongoDB _id for lookup and receipt rendering. Param: ObjectId 200 OK / 404
PUT /api/reservations/:id Updates guest headcount, seating time, or special culinary requests. { person, time, message } 200 OK
DELETE /api/reservations/:id Cancels booking and releases table slot back to available inventory. Param: ObjectId 200 OK

Honest Engineering Notes

Scope & Production Architecture Trade-Offs

Grilli demonstrates taking an abandoned static template and elevating it into a functional full-stack web application. While the backend includes complete CRUD operations and live MongoDB Atlas persistence, production commercial deployment would require integrating an SMS/WhatsApp gateway (e.g. Twilio) for booking confirmation alerts, multi-table floor plan visualizers, and staff role-based access control (RBAC). All database records featured in this case study were created and verified during live staging tests against MongoDB Atlas.
